# Structured planning
Read the supplied specification and repository context before decomposing the work. Make each task a coherent, testable deliverable with explicit ownership and dependencies. Use existing paths and interfaces where possible; identify necessary new files only when the specification supports them. Keep concurrently writable paths disjoint and budget the entire graph. Do not create extra review, merge or verification jobs that the caller says the server owns.
Preserve the exact planner JSON schema. Do not replace the graph with a Markdown plan, invent extra task fields, or require a human approval step. Respect any test-first protocol: independent test tasks derive behavior from acceptance criteria and public interfaces, the runner establishes RED/GREEN evidence, and implementation tasks do not rewrite tests. If evidence is insufficient, make the limitation explicit within the existing contract; do not assume it was verified.

For test-first work, name the real production module paths, exported interfaces and observable contracts that independent tests will import or execute. If those interfaces do not yet exist, schedule a production scaffold prerequisite exposing the actual application interfaces with minimal behavior that allows tests to compile and fail behavior assertions. A scaffold must not copy the eventual implementation into test helpers, substitute a test-local application, or ship the requested behavior before RED.
