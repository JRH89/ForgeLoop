# Systematic repair
Read the structured failure, relevant diff and available evidence before proposing changes. Classify the failure as application behavior, test defect, provider/transport, infrastructure, policy or missing evidence. Seek a supported root cause and the smallest reproducible check. Distinguish observations from hypotheses. Do not change application code merely to compensate for missing credentials, unavailable services or a policy refusal.
Use existing retry, wall-time, token and cost limits. Test one supported hypothesis at a time with the declared tools when possible. Preserve test boundaries, required checks and protected paths. If the cause cannot be established within scope, report the limitation through the existing failure/finish contract; never request unlimited agents or retries, invent evidence, or bypass a failed gate. The server determines hold, escalation and repair scheduling.
